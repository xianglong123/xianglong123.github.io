# GitHub Actions 当定时任务用

用 Actions 的 `schedule` 触发跑定期任务（抓数据、生成报表、检查站点），是个门槛极低的方案。但把它当 cron 用之前，得先知道它和真 cron 的差别。

## 五个必须知道的边界

### 1. cron 是"尽力而为"，不保证准时

官方明确说过定时触发可能延迟，负载高峰时延迟十几分钟很常见，个别情况更久。所以：

- **不要依赖精确时刻**。任务里如果要"取当天零点数据"，自己算，不要假设触发时就是零点。
- **重要任务加一个兜底触发**，比如另一个时间点跑一次，用幂等逻辑去重。

### 2. 仓库 60 天无活动，定时任务会被停用

公开仓库的 `schedule` 在 60 天没有任何 commit 活动后会被自动禁用。如果任务是"有变化才提交"，很可能几十天不提交，然后任务静默停掉。

规避方式：定期做一次空提交、或者任务里更新一个心跳文件。

### 3. 免费额度和私有仓库不一样

公开仓库的标准 runner 免费不限量；私有仓库按账户额度计费。长期跑高频任务（比如每 15 分钟一次）会吃掉大量额度。做数据采集这类任务，公开仓库更划算，但要注意别把敏感配置放进去。

### 4. 无状态，每次都是干净环境

每次运行都是全新容器：上次写的文件、装的包、缓存的登录态全没有。

能用的持久化只有三种：

- 提交回仓库（简单，但会污染历史）
- Actions Cache（有大小和淘汰策略，不能当数据库）
- 外部存储（对象存储、数据库、Gist）

### 5. 默认 token 权限很有限

`GITHUB_TOKEN` 只对当前仓库有权限，且默认只读。要 push 回去得显式声明：

```yaml
permissions:
  contents: write
```

要访问其他仓库或者调 API，才需要 Personal Access Token。这类 token 放 Secrets，不要写在 workflow 文件里。

## 一个能长期跑的最小结构

```yaml
name: collect
on:
  schedule:
    - cron: '0 */6 * * *'   # 注意是 UTC
  workflow_dispatch:         # 留个人工触发入口，调试必需
jobs:
  run:
    runs-on: ubuntu-latest
    permissions:
      contents: write
    steps:
      - uses: actions/checkout@v4
      - run: ./scripts/collect.sh
      - run: ./scripts/commit-if-changed.sh
```

`workflow_dispatch` 那一行很重要。调试的时候你不可能等到下一个定时点，有手动触发入口，一次排查能从半小时降到两分钟。

## cron 表达式有个坑

Actions 的 cron 用 **UTC**，不是本地时间。国内要跑"每天早上 8 点"，得写 `0 0 * * *`（UTC 0 点 = 北京 8 点）。

夏令时地区更麻烦，一年要改两次。用 UTC 固定时间、或者干脆按"每 N 小时"跑，比绑死本地时刻稳。

## 什么时候该换方案

出现这些信号时，说明该上真服务器了：

- 需要任务间隔小于 5 分钟
- 需要单次运行超过 6 小时
- 需要常驻进程（WebSocket 监听、长轮询）
- 需要本地磁盘长期保存中间文件
- 任务必须准时

一台最便宜的云主机 + `systemd timer` 或 `cron`，能覆盖上面全部需求，成本一个月几十块。**别为了省这点钱，把一个应该常驻的服务硬塞进 Actions。**
