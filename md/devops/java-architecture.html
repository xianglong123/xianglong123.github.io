两套 Java 大项目架构：电商交易中台与 SaaS 多租户

2026-11-25 · 后端架构 · 两套分层架构图（1280 宽）

整理大项目架构时，先把分层定下来：流量从哪进、外部依赖从哪出、核心业务域怎么切、共享能力下沉到哪一层。下面两套是同一套分层思路的两种落地——一套面向电商交易，一套面向 SaaS 多租户。图里的模块是候选边界，不是一开始就要全部拆成独立服务。

一、电商交易中台

图 1：电商交易中台分层架构（接入 / 网关 / 核心交易域 / 营销域 / 中间件 / 数据 / 基础设施）

这套按交易链路组织，从上到下七层：

  • 接入层：C 端 App/H5/小程序/Web、B 端运营与商家后台、开放平台、异步回调。
  • 网关层：入网关统一收口路由、鉴权、限流熔断、灰度与防刷；出网关作为防腐层，封装支付、短信、物流、地图等外部渠道，统一做签名、超时重试、熔断降级与调用审计。
  • 核心交易域：用户、商品、库存、订单、支付、履约物流、结算账务，各自围绕自己的业务闭环。
  • 营销域：活动中心、优惠券、秒杀抢购、拼团分销、积分，独立成域，可单独扩缩容与灰度。
  • 中间件中台：注册配置、消息队列、分布式缓存、检索、分库分表、对象存储、定时任务、分布式事务、链路追踪、日志与监控。
  • 数据存储：MySQL 分库主从、Redis、ES、OSS、离线数仓 BI。
  • 基础设施：容器编排、CI/CD、多环境隔离、安全防护。
两条域间约定：营销域不直接写交易库，通过订单事件加营销核销接口交互；外部渠道全部经出网关防腐层接入，业务服务不直连第三方。

二、SaaS 多租户平台

图 2：SaaS 多租户分层架构（平台核心域 / 计费订阅域 / 多租户隔离 / 中间件 / 数据 / 基础设施）

这套的重心不在交易履约，而在租户隔离与订阅计费：

  • 租户识别在网关完成：按子域名、Header、路径或 Token 解析出租户，租户 ID 全链路透传，再按租户映射到对应库或实例。
  • 平台核心域：租户中心（开通/冻结/注销、套餐绑定、配额）、账号权限（平台与租户双角色分权）、组织架构、可插拔工作台、消息通知、文件附件。
  • 计费订阅域：套餐商品、订阅订单、支付账单、用量计量、发票合同，与核心域通过事件解耦。
  • 多租户隔离：贯穿网关、服务、持久层与缓存，保证租户数据互不可见、配置互不影响。

数据隔离一般分三档，按租户规模和合规要求选：

隔离策略做法适用
共享库 + 行级隔离所有租户同库同表，靠 tenant_id 过滤中小租户，成本最低
共享库 + 独立 Schema同库不同 Schema，表结构各自独立中型租户，需要一定结构隔离
独立库 / 独立实例大客户专属库甚至专属部署合规要求高、体量大的租户

缓存 key 带租户前缀、ES 按 tenant_id 索引隔离、对象存储按租户目录隔离、定时任务按租户分片——隔离不是只在数据库做一层，而是每一层都要带上租户维度。

三、两套图的共同判断

这两张图都按微服务范式组织，但图上画了多少模块，不等于就已经是微服务。判断是不是真微服务，看四条硬标准：

  1. 独立部署与扩缩容：每个服务能单独发版、单独扩容，不绑死在一个进程里。
  2. 数据自治：服务独占自己的库，跨域只走接口或事件，禁止跨库 join、直连别人的表。
  3. 进程间通信：同步 RPC、异步 MQ，而不是同进程内直接调方法。
  4. 故障隔离：一个服务挂了不拖垮整条链路，有熔断、降级、舱壁。

落地时不必一步拆成图上那么多服务。起步更适合先做模块化单体：代码按域划包、边界清晰、库表按域归属，等某个域确实有独立扩容或独立发版诉求时，再沿着这些边界拆。图里的域划分，正好就是未来拆分的候选边界。

微服务真正的成本不在画图，而在分布式那摊事：分布式事务、跨域查询、分布式锁、链路追踪、配置与灰度一致性。图里中间件层标了对应组件，但选型和补偿方案才是难点。
