# 国密 SM2 / SM4 在纯前端怎么做

国密算法工具站的典型形态：用户粘贴一段密文、一把密钥，浏览器里算完直接显示结果，服务端什么都不留。

技术上完全可行，但有几个地方做错就会得到一个"看起来能用、实际上换个人解密就失败"的工具。

## SM2：非对称，别把它当 RSA 用

SM2 是椭圆曲线公钥算法，能做签名和加密。三个最容易踩的点：

### 1. 密文格式有 C1C2C3 和 C1C3C2 两种顺序

这是互操作性问题的第一大来源。老版实现（包括部分库的默认行为）输出 `C1C3C2`，国密标准要求 `C1C2C3`。

症状很典型：自己加密自己解密完全正常，跟别人的系统对接就报错。**解密端必须先问清楚对方是哪种顺序，工具里最好提供一个格式开关**，两种都支持。

还有 C1 点是否带 `04` 前缀的问题。压缩点的表示里 `04` 表示非压缩，某些实现输出的密文包含它，某些不包含。跨系统对接时这也是必查项。

### 2. 随机数必须来自密码学安全的源

SM2 加密过程依赖随机数 k。用 `Math.random()` 生成 k，会得到一个**能通过自测、但密码学上已经破了**的实现。浏览器里要用 `crypto.getRandomValues`。

同理，密钥生成也不能用普通随机。私钥的熵不足，暴力搜索的成本会从"不可能"降到"可行"。

### 3. 私钥别碰服务端

纯前端做 SM2 的最实际价值就在这里：私钥只在浏览器内存里存在，不经过网络、不落盘、不进日志。

对应要做的两件事：

- 刷新页面即清空（不要用 localStorage 存私钥，那是把风险从服务端搬到本地）
- 不要把输入内容拼进任何请求 URL 或错误上报里

## SM4：分组密码，模式比算法更容易错

SM4 是 128 位分组、128 位密钥的分组密码。算法本身没什么选择空间，但**使用模式**选择很多，而模式决定了互操作性。

要点：

- **默认用 CBC + PKCS7 填充**，这是国内系统里最常见的组合。ECB 不要作为默认选项（相同明文块产生相同密文，会泄露结构），但可以留一个"兼容旧系统"的入口。
- **IV 的处理方式要明确**。常见做法是把 IV 明文拼在密文前面，解密端取前 16 字节。如果对方是固定 IV，要显式标注这是不安全用法。
- **编码要能对上**。密文输出 Base64 还是 Hex、是否大写、是否带换行和空格，任何一项不一致都会让对接方以为"算法不对"。

## 一个工具站的正确姿势

界面按"输入区 / 参数区 / 结果区"三段走，参数区默认值取最常见组合，并提供"高级"展开。

比界面更重要的是**正反验证**：加密完成后，提供一个"用这段密文解回去"的按钮。用户不需要理解算法，只需要看到"能回来"就能确认工具是对的。这比写十段算法说明有用。

## 前端能不能算得动

能。SM4 加密一段几 KB 的文本，浏览器里是毫秒级。真正需要担心的不是性能，而是**大文件**：超过几 MB 时逐块处理要注意内存峰值，用流式或分块加解密，避免一次性把整个字符串摊在内存里。

SM2 的性能要弱一些（椭圆曲线运算），但它本来就不是拿来加密大段数据的用途——正确用法是"SM2 加密一个对称密钥，SM4 加密正文"。工具站上应该把这层语义讲清楚，否则用户会拿 SM2 去加密整篇文章，然后抱怨慢。
