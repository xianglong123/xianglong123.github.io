用 GitHub Actions + Pages 做数据站 ​

想要一个"每天自动更新、有人访问、零成本"的数据站点，GitHub Actions 加 Pages 是目前最省事的组合。它不需要服务器、不需要数据库、不需要运维，代价是有明确的边界。

整体结构 ​

定时触发（cron）
  → 拉取数据（API / 抓取）
  → 归一化成 JSON
  → 写入仓库（data/ 目录）
  → 提交 & push
  → Pages 自动发布静态站

站点是纯静态的，前端读 data/xxx.json 渲染。没有后端，所以也不会有注入、越权、数据库泄露这些问题。

数据层设计要点 ​

1. 快照 + 索引，而不是只存最新 ​

只覆盖写最新一份，历史就没了。正确做法是两份：

  • data/latest.json —— 最新快照，供页面直接读
  • data/archive/YYYY-MM-DD.json —— 按日期归档，供趋势和回溯

归档文件会让仓库变大，但文本 JSON 压缩率很高，正常规模几年也就几十 MB。

2. schema 稳定比内容丰富重要 ​

前端是按字段读的，一旦字段改了，历史归档就全部读不了。所以：

  • 字段名不要随心情改
  • 新增字段可以，删除字段要谨慎
  • 在 data/schema.json 里写清楚每个字段的含义和类型

3. 幂等：同一份数据不要重复提交 ​

定时任务最常见的问题是空转——数据没变化，还是提交一次，仓库历史被无意义的 commit 塞满。

处理方式：生成完 JSON 后先 git diff 检查，无变化就退出。

bash
if git diff --quiet data/; then
  echo "无变化，跳过提交"
  exit 0
fi

抓取侧的三个现实问题 ​

失败要可观测 ​

外部 API 挂掉、返回结构变了、被限流，都会让任务失败。别让失败静默：任务失败时保留上一次成功的数据，同时在页面上显示数据时间戳。用户看到"数据更新于 2 天前"，比看到空白页或者错误数据要好。

限流要提前规划 ​

免费 API 普遍有速率限制。Actions 的定时任务每天跑几次不会触发限制，但如果一次要抓几百个条目，就要加延时和重试。对同一域名高频请求，很容易被封 IP —— Actions 的出口 IP 是共享的，被封的概率比自家服务器更高。

依赖数据的许可 ​

抓别人的数据做站点，先看清楚对方 API 的使用条款。很多免费 API 明确禁止商用或者要求署名。这件事在技术上做起来没有门槛，在合规上不是。

这套方案的边界 ​

适合：低频更新（每小时一次以内）、数据量中等（几 MB）、只读展示。

不适合：

  • 需要秒级更新
  • 需要用户交互（登录、写入）
  • 数据量到几百 MB 以上（仓库会变慢，Pages 也有大小限制）
  • 需要保密的数据（仓库公开就是公开的）

一旦越过这些边界，就该上真正的服务器和数据库了。但在"验证一个数据产品有没有人看"的阶段，这套方案的性价比没有对手。
