# MCP 为什么值得用

MCP（Model Context Protocol）是给"模型调用外部工具"这件事定标准的一套协议。在它之前，每个项目都在自己写一套：A 项目里工具是 JSON、B 项目里是函数签名、C 项目里又变成 prompt 里写死的调用格式。

## 它解决的问题不是"调用"，是"复用"

单个项目里，工具调用怎么写都行。真正麻烦的是这三种场景：

1. **同一个能力要接多个客户端**（今天接桌面端，明天接聊天机器人，后天接 IDE）。
2. **多个工具要组合使用**（读文件、查数据库、调 HTTP，分别来自不同实现）。
3. **换模型或换框架时不想重写工具层**。

没有标准的时候，一个工具的实现只在它那套框架里有效。有标准之后，工具是独立进程（server），客户端按协议去发现和调用它，换框架不用动工具代码。

## 三个核心概念

- **Server**：提供工具的一方，可以是本地进程（stdio）或远程服务（HTTP/SSE）。
- **Client**：宿主程序，负责连接 server、把工具列表交给模型。
- **Resources / Tools / Prompts**：三类暴露物。Tool 是模型可以主动调用的动作；Resource 是可读的数据（文件、记录）；Prompt 是预设的提示模板。

分这三类的意义在于**权限粒度不同**。Resource 是只读的、由应用决定何时读取；Tool 是模型主动发起的、可能有副作用。把它们混在"函数"里，就没法在协议层做权限控制。

## 实践里最值得的两点

**一，工具发现是动态的。** 客户端不需要预先知道有哪些工具，连上 server 后拉列表。这让"给一个 Agent 临时加能力"变得很轻——加一个 server 配置，能力就多了一组。

**二，stdio 传输让本地能力可复用。** 本地文件系统、本地数据库、本地 CLI 工具，都能被包成一个本地 server，然后被任何支持 MCP 的客户端使用。这是它比纯远程 API 更有意思的地方。

## 什么时候不值得上 MCP

- 只有一两个工具，且只在一个应用里用。直接写函数调用更简单。
- 需要极低延迟。多一层协议和进程通信，开销不划算。
- 团队里没人维护 server 进程的生命周期。

判断标准很简单：**工具会不会被第二个地方复用**。会，就值得；不会，先别引入复杂度。
