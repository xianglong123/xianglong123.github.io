# 飞书机器人接 Agent：一条消息的完整链路

把一个 AI Agent 接到飞书，表面上只是"收消息、发消息"两件事，实际要做对一整套时序。

## 链路全貌

```
用户发消息
  → 飞书回调（HTTP POST 到你的事件地址）
  → 验签 + 解密 + 去重
  → 立刻返回 200（3 秒内，超时会重推）
  → 消息进队列
  → Agent 异步处理
  → 用 message_id 回复到原会话
```

关键点：**回调处理必须快速返回，真正的推理放到异步**。飞书对回调有超时限制，超时后会重复推送同一条事件。很多人第一次接的时候在回调里同步跑模型，结果就是用户收到三条一模一样的回复。

## 三个必须处理的问题

### 1. 验签

飞书的回调带签名头，需要按官方给的算法用 `timestamp + nonce + 加密 key` 做校验。省掉这一步的直接后果是：任何知道 URL 的人都能伪造消息。

### 2. 去重

请求超时重推、网络重试、用户重复发送，都会出现同一条消息进来两次。用飞书事件里的唯一标识做幂等键，落库或放 Redis，处理前先抢锁。没有这一步，Agent 会对着同一条指令反复执行——如果它调的是写操作，后果就不是多发几条消息了。

### 3. 异步回复

回复要用原消息的 `message_id`（或者会话 id），而不是自己新建一个会话。注意区分这两种接口：

- 回复单条消息：引用原消息，上下文落在群里
- 主动发消息到会话：需要 bot 有对应权限，且可能触发限流

## 长任务怎么反馈

Agent 处理超过十几秒时，用户会觉得"它卡住了"。这里有两个方案：

**方案一，先确认再推送。** 收到消息立刻回一句"收到，正在处理"，处理完再发结果。用户的等待焦虑会明显下降。

**方案二，分步播报。** 如果 Agent 是多步任务（查资料→写稿→发布），每一步完成后往会话里发一条进度。适合耗时几分钟的任务。

两种都要注意消息频率。飞书对单个 bot 的发送有速率限制，高频短消息很容易被限流，宁可合并成一条卡片消息。

## 内网穿透的取舍

本地开发要接回调，就得把本地端口暴露出去。可选方向：

- 反向代理 / 隧道服务（一次性 URL，方便但每次要换）
- 自己有服务器（域名 + HTTPS，稳定，但要维护证书和进程）
- 云函数做轻量转发（省运维，但调试不便）

如果 Agent 本身要访问本地资源（文件、内网服务、桌面应用），纯云函数方案跑不通，还是得有一台常驻机器。这种时候用自己服务器 + 隧道兜底最实际。

## 一个容易忽略的点

在群里 @ 机器人和私聊机器人，事件的字段结构不完全一样。私聊拿到的 `chat_id` 和群聊拿到的 `chat_id` 格式不同，如果代码里假设了"一定是群"或"一定是单聊"，就会在另一种场景下静默失败。先按两种都处理，再逐步收敛。

同理，消息里的 @ 提及、富文本、图片、文件，事件体结构都不同。一开始就写一个归一化层（把各种消息类型统一成 `{text, attachments}`），后面接 Agent 时省大量重复判断。
