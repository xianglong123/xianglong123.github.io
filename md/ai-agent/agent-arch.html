Agent 的三层结构：模型、工具、编排 ​

一个能长期稳定运行的 Agent 系统，几乎都能拆成三层。分层不是洁癖，它的实际价值是：出问题时你知道该改哪一层，而不是所有东西一起改、一起猜。

第一层：模型，只做它擅长的部分 ​

模型的强项是意图理解、歧义消解、把自然语言映射成结构化参数。弱项很明确：

  • 精确算术和字符级处理
  • 跨轮次的状态一致性
  • 长链路的自洽（超过十几步之后，它对"自己已经做过什么"的认知会开始漂移）

对应三条工程约定：

  1. 要精确结果的计算交给工具，不要让模型心算。汇率、金额、日期差这类东西，一旦让它推导就会出错，而且错得很有说服力。
  2. 跨轮次的状态存在编排层（数据库、KV、文件），不要指望对话上下文记住。上下文会被截断、会被压缩，写进去的东西不保证还在。
  3. 要严格格式的输出用 schema 约束，不要只写一句"请输出 JSON"。给工具定义 JSON Schema，让运行时去校验和重试，比在 prompt 里反复强调可靠得多。

第二层：工具，描述质量决定成功率 ​

工具层最常见的错误，是把内部函数的签名直接暴露给模型。比如一个 query(sql) —— 对模型来说，这是一张空白支票。

工具描述要写清楚四件事：

  • 什么时候该用它（触发条件的自然语言描述）
  • 参数的含义和取值边界（不是类型，是语义。date 是"YYYY-MM-DD 格式的日期，不能是未来时间"）
  • 成功返回什么
  • 失败时返回什么，模型该怎么做

最后一条最容易被忽略。工具失败时如果只返回一句 error，模型只能猜或者重试。返回结构化的失败原因（比如 {"error": "not_found", "hint": "该订单不存在，可以用 order_list 按用户查"}），重试的成功率会明显不一样。

还有一个实用原则：工具数量控制在模型能一次看全的范围。二三十个工具之后，选择困难会直接变成错误率。宁愿做参数更多的少数工具，也不要摊成一堆细碎的工具。

第三层：编排，真正决定鲁棒性的地方 ​

编排层要回答四个问题：

  1. 循环怎么转：单轮调用、ReAct 式交替、还是固定的 workflow 图。
  2. 什么时候停：最大步数、最大耗时、以及"模型认为完成"之外的独立判据。
  3. 失败了怎么办：重试策略、降级路径、要不要人工接手。
  4. 可观测性：每一步的输入输出有没有落盘，能不能回放。

其中第 2 条最容易被做错。只靠"模型说完成了"来结束，会遇到两种病：提前宣布成功，或者永远停不下来。加一层独立校验（比如检查产出物是否真的存在、字段是否齐全）比调 prompt 有效。

第 4 条是排障的前提。Agent 出错时你面对的是一个十几步的链路，没有每步的输入输出记录，基本只能重跑猜。把 trace 落地成文件或表，一次踩坑的代价能摊到后面所有次。

三层的责任边界，一句话总结 ​

  • 模型：判断意图、决定下一步动作
  • 工具：把外部能力变成有明确契约的接口
  • 编排：控制流程、保存状态、兜住失败

哪一层越界，系统就会在某个具体场景里崩掉。模型做了工具该做的精确计算，会算错；工具承担了编排的职责（比如自己重试三次），会拖垮整个链路；编排让模型决定终止，会停不下来。
